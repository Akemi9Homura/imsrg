# 测试

## 1. 运行

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 4
PYTHONPATH=$PWD/build/src ctest --test-dir build --output-on-failure        # 全部（约 7 分钟，MRCorrelatedDriver 约 6 分钟）
PYTHONPATH=$PWD/build/src ctest --test-dir build -R '^MR' -E Correlated      # MR 快速子集
```

- Python 测试 `import pyIMSRG`，需要 `PYTHONPATH` 指向 `build/src`（`pyIMSRG.so` 所在目录），且必须是绝对路径：上游测试的工作目录不在仓库根，相对路径会让它们找不到模块（MR 测试在 CMake 里自带路径）。
- 很多测试用 `prototype/mrimsrg/data/` 下的参考态夹具（m-scheme NCSM 波函数与密度）。这些数据不在仓库里：本机是指向
  `~/mr-imsrg/prototype/mrimsrg/data` 的符号链接，**不要提交**。
  BIGSTICK 夹具 `test/data/bigstick_He4_Nrefmax2/` 在仓库里（小文件）。`MRThreeBody` 还需要数据目录里的
  `N3LO_lnl_3N/`（集群 `/tns/public/Forces/N3LO_lnl/3BME/` 中 emax6、ħω16 的 full 与 NO2B 两个文件，共 2.2 MB），缺失时直接报错。
- 比较多线程结果时设 `OPENBLAS_NUM_THREADS=1`（见 性能与并行.md）。

## 3. 各层验收的对应关系

| 层 | 基准 | 测试 |
|---|---|---|
| 密度与 J 耦合 | m-scheme 原型 | MRPrototype、MRReference、MRBigstickReference |
| λ2 对易子（标量） | 慢速 C++ / Python J-scheme / m-scheme 镜像 | MRReference |
| λ2 对易子（张量） | 稠密 m-scheme oracle | MRTensor |
| SR 退化 | SR 驱动 | MRReference（逐位）、MRSRDriver |
| 生成元 | m-scheme oracle | MRReference、MRDenominators |
| Magnus/BCH | 矩阵元 oracle | MRMagnus |
| 驱动与导出 | Python 原型、往返核对 | MRDriver、MRCorrelatedDriver |
| 完整流与下游谱 | 存档的正式结果 | 集群复跑（[验收结果](../MR-IMSRG-验收结果.md)、计划 9.5 节），不在 ctest |

## 4. 改代码后跑什么

| 改了 | 至少跑 |
|---|---|
| `MRReference`、jref 工具 | MRReference、MRReferencePairOrder、MRBigstickReference、MRGuards、MRThreeBody |
| `MRThreeBody`、`lambda3.py`、λ3 对易子项 | MRThreeBody、MRBigstickReference |
| `MRCommutator` 标量部分 | MRReference、MRMagnus、MRCorrelatedDriver |
| `MRCommutator` 张量部分、`TensorCommutators.cc` | MRTensor、MRSRDriver、上游 Tensor/UnitTestTensor/UnitTestComm122st |
| 生成元 | MRDenominators、MRReference、MRTailDiagnostic |
| 驱动、求解器 | MRDriver、MRSRDriver、MRGuards、MRCorrelatedDriver |
| `gen_job.py` | MRJobGenerator |

改动可能影响长流结果时，再用集群复跑对照存档（计划 9.5 节的做法）。
